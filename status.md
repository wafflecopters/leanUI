## Architecture: the proof controller (`src/controller/`)
The proof editor is a **headless controller with a thin UI on top**, not a React component that happens to call Lean.

- **`ProofSession`** owns everything semantic about editing one declaration's proof: tree + cursor + selection + history, the goal round-trip, candidate generation, validation, write-back. Lean arrives through an injected `LeanAnalyzer`, so the same session runs in a browser (`httpAnalyzer`), under Node against real Lean (`nodeAnalyzer`), or against a scripted fake (`testing.ts`). Every round-trip is awaitable — `await session.refresh()` settles, so tests assert on state, never on timing.
- **`getState()` is plain serializable data**, including `actions`: the explicit list of moves available right now, each with the arguments it needs and the values valid for them. That list is the contract — a UI renders it, a test asserts on it, an agent picks from it.
- **Drive it without a browser:** `npx tsx scripts/proof-repl.ts --decl limitAdd` (interactive) or `--run "constructor; intros ε epsPos; have h1 : 0 < ε / 2; take apply divTwoPos; take assumption; proof"`.
- Layers, each independently testable: `candidates` (what's worth trying) → `discover` (what Lean's own search finds) → `validate` (what actually works, + previews) → `actions` (what's possible) → `session` (state + dispatch). `useProofSession` is the entire React surface.
- **Tests:** `npm test` is the fast gate (~1s since M5 removed the TT compiler suites; excludes `*.e2e.test.ts`); `npm run test:e2e` runs the real-Lean suites — **file-serial** (`fileParallelism: false` under `E2E=1`), because each e2e file's fork spawns its own Lean worker pool and a Mathlib-loaded pool is multiple GB. Mathlib e2e runs are expensive by nature: expect one ~5–7GB resident Lean process while they run — always launch them through `scripts/guarded-run.sh -l 14 --`, which kills the process tree if it passes the limit.

- **"Compute" — the clicked subterm reduces (`2 + -1` → `1`).** Root cause of the dead pills: the preset's numerals live in TWO term forms — a user-typed `2` is `OfNat.ofNat 2`, a lemma-substituted one is `rtwo R` — identical in display (unexpanders), disjoint for syntactic matching, so every lemma stated on one form silently missed goals holding the other (probed empirically: `unfold rtwo` fails on literal goals, `rw` never crosses forms, simp does not see through the instance). Fix keeps the engine pure: the PRESET gains `@[simp]` literal-bridges (`(2 : Carrier R) = rtwo R := rfl`), a real proof of `addSumNeg` (was `sorry`) + `negLeft`, and the `@[simp]` fact `twoAddNegOne : 2 + -1 = 1`; the ENGINE gains a generic Compute candidate — scoped `conv in (sub) => simp` with a whole-goal `simp` twin under one label (the conv pattern is syntactic and misses constant-form goals; dedupeByLabel keeps whichever fired). Plain `simp` is the protocol: the file's @[simp] set defines what "compute" means, Mathlib's default simp set slots in identically. Verified against real Lean in all three term forms (new e2e test) + candidates unit tests; sorry-free via `#print axioms`.
- **The ~100GB memory blowup is fixed at the source.** Root cause (two incidents, 2026-07-28): a Lean process that imports Mathlib holds 4–7GB resident; the bridge's single shared pool of 3 `extract --serve` workers all got warmed to Mathlib size, busy workers spilled into 4–7GB one-shot spawns, and parallel e2e forks (plus the dev server) each stacked their own copy of all that. Fix: the bridge now runs **separate core and Mathlib pools** — Mathlib defaults to ONE worker (`LEANUI_MATHLIB_WORKERS`, core pool via `LEANUI_EXTRACT_WORKERS`) with its own concurrency limiter sized to the pool, so excess Mathlib work queues instead of spawning; warm-up touches only the matching pool; the legacy `checkLeanSource` Mathlib path holds a slot too; and e2e runs are file-serial. Worst case per process went from ~22GB+ to ~one Mathlib worker. Also: never `claude --resume` a session that died mid-e2e with auto-mode — its first act is to re-run the e2e.
- **One editor for the own-axioms user AND the Mathlib user — capability is discovered, never declared.** Suggestions were tuned entirely against a from-scratch axiomatisation of ℝ, where `exact?` finds nothing and `rw?` doesn't exist; that shaped the whole engine around ranking the file's own lemmas. The fix is not a mode switch: `SOLVER_TACTICS` now proposes core Lean (`rfl`, `trivial`, `decide`, `omega`) and Mathlib (`norm_num`, `positivity`, `linarith`, `ring`, `nlinarith`) side by side on every goal, and `rw?` rejoined the discovery probes — with nothing anywhere asking which is loaded. Validation already answers that question honestly: an unavailable tactic is an error at its own line, the same signal as a lemma that fails to apply, so it's dropped by the same code. Measured against core Lean to confirm the mechanism: an unknown tactic reports `unknown tactic` at its line PLUS a knock-on `unsolved goals` at the `by` — which is exactly why `validateOne`'s check must stay scoped to the tactic's own line, now documented as load-bearing and covered by tests. Verified live: the real-analysis preset shows no phantom Mathlib pills. The payoff is that supporting a library costs one failed trial, not a branch — and the file-lemma ranking stops being a substitute for missing tactics and becomes what it should be, the thing that finds the user's OWN lemmas.
